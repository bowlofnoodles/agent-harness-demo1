# Agent Harness Demo

A React frontend project built with harness engineering principles — designed so AI coding agents work effectively within well-defined constraints, feedback loops, and verification systems.

## Tech Stack

- **Framework**: React 19 + TypeScript (strict mode)
- **Build**: Vite 8
- **Styling**: Tailwind CSS v4 + shadcn/ui
- **Testing**: Vitest + React Testing Library
- **Linting**: ESLint with typescript-eslint + react-hooks + react-refresh
- **Git Hooks**: Husky + lint-staged (pre-commit runs lint)

## Commands

```bash
npm run dev          # Start dev server
npm run build        # Type-check + production build
npm run typecheck    # TypeScript type checking only
npm run lint         # ESLint
npm run test         # Run tests once
npm run test:watch   # Run tests in watch mode
npm run verify       # Full pipeline: typecheck → lint → test
```

**IMPORTANT**: Always run `npm run verify` after making changes to ensure nothing is broken. This is the primary feedback sensor.

## Project Structure

```
src/
├── components/       # Reusable UI components
│   ├── ui/           # shadcn/ui primitives (DO NOT manually edit)
│   └── layout/       # Layout components (header, sidebar, etc.)
├── pages/            # Page-level components (one per route/view)
├── hooks/            # Custom React hooks
├── types/            # TypeScript type definitions
├── lib/              # Utility functions
└── test/             # Test setup and shared test utilities
```

## Architecture Rules (Constraints)

These rules define the boundaries that agents MUST respect:

1. **Component hierarchy**: `pages/` → `components/` → `components/ui/`. Never import upward.
2. **shadcn/ui components** (`src/components/ui/`): Generated by `npx shadcn@latest add <component>`. Do not hand-edit these files.
3. **Path aliases**: Always use `@/` imports (e.g., `@/components/ui/button`), never relative paths crossing directories.
4. **Type safety**: TypeScript strict mode is on. No `any` types. No `@ts-ignore`. No type assertions unless truly necessary (with a comment explaining why).
5. **State management**: Use React's built-in state (useState, useReducer, useContext) for now. Do not add external state libraries without explicit approval.
6. **Styling**: Use Tailwind utility classes. No CSS modules, no inline style objects, no custom CSS files (except `index.css` for Tailwind config).

## Verification Checklist (Sensors)

Before considering any change complete, verify:

- [ ] `npm run typecheck` passes with zero errors
- [ ] `npm run lint` passes with zero errors
- [ ] `npm run test` passes with zero failures
- [ ] New components have at least one test covering the main use case
- [ ] No `console.log` left in committed code (use it for debugging, remove before committing)

## Patterns to Follow (Guides)

### Adding a new component
1. Create file in `src/components/<name>.tsx`
2. Export a named function component (not default)
3. Define props interface in the same file
4. Write a test in `src/components/<name>.test.tsx`
5. Run `npm run verify`

### Adding a new page
1. Create file in `src/pages/<name>.tsx`
2. Compose from components in `src/components/`
3. Wire into `App.tsx`
4. Write a test covering the page's key interactions
5. Run `npm run verify`

### Adding a shadcn/ui component
```bash
npx shadcn@latest add <component-name>
```
Do not create UI primitives by hand.

## Feedback Loop

When `npm run verify` fails:
1. Read the error output carefully
2. Fix the root cause (don't suppress errors with `@ts-ignore` or `eslint-disable`)
3. Re-run `npm run verify` to confirm the fix
4. If a test fails, understand WHY it fails before changing the test — the test might be correct and the code wrong

## What NOT to Do

- Do not install new dependencies without clear justification
- Do not refactor working code unless specifically asked
- Do not add abstractions "for the future" — build what is needed now
- Do not disable TypeScript strict checks or ESLint rules
- Do not create files outside of `src/` (except config files at root)
